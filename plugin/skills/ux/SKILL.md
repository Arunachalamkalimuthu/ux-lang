# Writing .ux

`.ux` describes what an interface **means** — screens, what is on them, what a
user can do, and where each action leads. It does not describe styling.

Write the `.ux` first. Generate code from it second. The `.ux` file is the
source of truth; generated code is output.

## Grammar

Two-space indentation, no tabs. `#` starts a comment. No imports — names
resolve across the whole project.

```
app Name              # or: site example.com

data Name
  field  type  required      # required | = default | type? | [type]
  status one of a | b = a
  owner  User                 # a PascalCase name references another data
  tags   [text]                # a list of a primitive type

screen Name(param)
  at /path                    # optional
  needs signed-in             # optional
  intent "why this screen exists"   # REQUIRED, one line

  heading "Title"
  text "Some copy"
  show expr
  group "Section"
    ...
  tabs One | Two
    -> Two
  if condition
    ...
  else
    ...
  action "Label" -> Target        # button, link, and nav are all `action`
  action verbName                 # bare verb: calls flow `verbName`, no args
  action verbName(arg)            # bare verb, with args
  use ComponentName(arg)

  form DataName            # fields are real names from `data DataName`, not the word "field"
    title required
    due
    submit "Label" -> flowName(arg)

  list DataName where cond
    sort by fieldName
    row fieldA, fieldB
    tap -> Screen(arg)
    empty   "…"  action "…" -> Screen    # REQUIRED
    loading skeleton 3 rows              # REQUIRED
    error   "…"  action retry            # REQUIRED; `retry` is built in

component Name(param)
  ...                        # same elements as a screen body

flow name(arg)
  set thing.field = value
  call api.method(arg)
    ok   -> toast "Done" undo 5s
    fail -> error "Message"
  go ScreenName
```

Types: `text number int bool date time datetime money email url phone image
file id secret`

## Rules that are enforced

- Every screen needs an `intent`. One line, plain language.
- Every `list` needs `empty`, `loading`, and `error`. This is the rule that
  matters most — building only the happy path is the usual failure, and here
  it will not check.
- Every screen needs a way out. `action`, `tabs`, a list's `tap` or state
  actions, and a `form`'s `submit` all count as a way out — a screen with
  none of these leading elsewhere is a user stuck, and `ux check` reports
  it. `retry` is built in and creates no navigation edge, so an `error`
  state that only offers `action retry` does not, by itself, satisfy this
  rule.
- Navigation targets must exist. A `-> Checkout` with no `screen Checkout`
  fails.

## Project layout

```
ux/
  app.ux                entry
  data/*.ux              or one data.ux
  screens/*.ux           one file per screen
  components/*.ux        only when 3+ screens use it
  .build/app.map          generated by `ux map`
```

## Workflow

1. Write or edit the `.ux` files.
2. Run `ux check ux/`. Fix every diagnostic — each one names the fix. Exit
   code is 0 only when there are no errors; this is the gate.
3. Run `ux map ux/` to see the whole navigation graph. It always exits 0,
   even on a broken project — it prints an error count instead of hiding
   them, but it is not the gate. Use `ux check` for that.
4. Generate code from the `.ux`. See `reference/codegen.md`.

When the user asks for a UI change, change the `.ux` first, re-check, then
regenerate. Never edit generated code and leave `.ux` behind — that makes the
source of truth a lie.
