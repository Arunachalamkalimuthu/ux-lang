ux-lang · Apache-2.0

A language for what your interface means.

.ux describes screens, what a person can do on them, and where every action leads. Then it catches the bugs a compiler normally can't — like a screen nobody can leave.

GitHub Try it below

Node 20+. Zero dependencies — nothing to install after the clone.

app Tasks

data Task
  title  text  required
  done   bool  = false
  due    date?

screen Inbox
  at /
  intent "See what's due and clear it"

  list Task where not done
    sort by due
    row   title, due
    tap   -> Detail(task)
    empty   "All clear."
    loading skeleton 3 rows
    error   "Couldn't load." action retry

  action "New task" -> NewTask
The problem

Nothing records what the app was supposed to be.

You prompt a screen into existence, then another. The model never sees the app as a system — so state contradicts itself across screens, a flow dead-ends, and a regeneration quietly drops a step nobody notices until a user does.

The generated code can't be the record. It's forty files of implementation, and no single one of them states the intent. A .ux file can be one page — short enough for a person to read in a minute and for a model to hold entirely in context.

app.map

    

      
The whole app, in four lines.


Inbox   -> Detail | NewTask
Detail  -> Inbox
NewTask -> Inbox

      

        Generated from the arrows. It's small enough to keep in context permanently, which is the point:
        a model editing one screen reads this plus the single file it's changing, and still reasons correctly
        about the entire app. It never has to load everything.
      

      
That's what lets this scale past a hundred screens without outgrowing a context window.

    

  


  

    
Diagnostics

    

      
Every error names its own fix.


inbox.ux:6  UX202  `Detail` has no way out — a user who lands here is stuck.
  fix:  add an action that leaves:  action "Back" -> Inbox

      

        

          
Built for a model to act on

          

            The fix: line exists so a model can self-correct without a human refereeing. Write, check,
            fix, repeat — the loop closes on its own.
          

        

        

          
34 rules, two layers

          

            One layer asks whether a file is well-formed. The other asks whether the names it references
            exist anywhere in the project. Half of what they catch are UX defects, not code defects.

Status

    

      
What's built, and what isn't.

      

        Built: the parser, both checking layers, the CLI, three worked example apps, the Claude Code plugin,
        and an adoption benchmark. The suite is green and the examples check clean.
      

      
Not built, and worth knowing before you invest:

      
    
        
  • 
          The Chrome indexer. Reading a live page into .ux, so an agent navigates a
          semantic index instead of the DOM. Specified in the design, not started.
        
    • 
        
  • 
          Search and filter-by-input. A list's where clause can't reference something the user
          just typed. The benchmark found this; there's no design for it yet.
        
    • 
        
  • 
          Drift protection. Nothing yet verifies that generated code still matches its .ux.
          It's a convention, not an enforcement.

Use cases

    
Where a .ux file earns its keep.

    

      The common thread: somebody needs to know what the app is supposed to do, and the code is
      the wrong place to ask. These are the situations where that costs you something real.
    

  


  

    
Building

    

      

        
The regeneration that loses a step

        

          You ask for a change to the checkout screen. The model rewrites four files, and the "resend
          verification code" link that used to sit under the phone field is gone. Nothing errored. No test
          covered it, because no test knew it was supposed to be there.
        

        

          This happens because the app's shape lives only in the generated code, and the model can't hold
          forty files at once. With a .ux file, the shape lives in one page it always sees. You change
          one line, regenerate, and what you didn't touch stays.

Review

    

      

        
Reviewing a flow before the code exists

        

          "Where does Cancel go?" is a product decision, but today it is only answerable by reading a
          component tree or clicking through a preview build. So it gets decided by whoever wrote the
          component, at 2am, by accident.
        

        

          A .ux diff shows a flow change as a flow change:
        


  screen Checkout
     intent "Take payment and confirm the order"
-    action "Cancel" -> Cart
+    action "Cancel" -> Catalog

        

          That is reviewable by someone who doesn't read React, in a pull request, before anything is built.

CI

    

      

        
Making a stuck user a failed build

        

          A screen with no way out isn't a crash. It renders, it passes type-checking, every unit test is
          green, and a person who lands there has to kill the app. Nothing in a normal toolchain has the
          concept needed to notice.
        


$ ux check ux/
ux/screens/confirm.ux:4  UX202  `Confirm` has no way out — a user who lands here is stuck.
  fix:  add an action that leaves:  action "Back" -> Cart

1 error(s)
$ echo $?
1

        

          Same for a link to a screen nobody wrote, a screen nothing links to, and a list with no empty
          state. All of them exit non-zero, so they fail the build like anything else.

Onboarding

    

      

        
Answering "how does this fit together"

        

          The first week on a new codebase is spent reconstructing a map that exists in nobody's head and
          no file. ux map prints it:
        


Catalog       -> Cart | ProductDetail
ProductDetail -> Cart | Catalog
Cart          -> Catalog | Checkout | ProductDetail
Checkout      -> Cart | Catalog

        

          Four lines, generated from the source, so it can't be out of date the way a wiki diagram always is.
          It's also what you hand a model before asking it to change anything.
        

      

    

  


  

    
Completeness

    

      

        
Forcing the states everyone skips

        

          Generated UI is almost always the happy path. The list renders beautifully with three items and
          has nothing to say when the fetch fails, the result is empty, or it's still loading — because
          nothing ever made anyone decide.
        

        

          In .ux a list without all three states doesn't check. It isn't a lint warning you can turn off;
          the file is invalid. It's the most opinionated rule in the language and the one that changes the
          most about what gets shipped.
        

      

    

  


  

    
Later

    

      

        
Agents that navigate a site instead of scraping it

        

          The same format read in the other direction: an indexer walks a live page's accessibility tree and
          writes .ux. An agent then plans a route through a semantic map — a few hundred tokens, stable
          across redeploys — instead of paying tens of thousands of tokens for DOM that is mostly class hashes.
        

        

          This is specified in the format design and deliberately not built. It's the larger half of the idea,
          and it needs the authoring half to be solid first.

The regeneration problem

    

      Ask an AI to change one screen and it rewrites four files. Something you never mentioned quietly
      disappears. This is not a model failure — it's a missing artifact.
    


    

      Here is the shape of it. You have a checkout screen. Under the phone field there's a
      resend verification code link, added three weeks ago after someone complained. You ask for
      an unrelated change: move the order summary above the payment form.
    

    

      The model rewrites the screen. The summary moves. The resend link is gone.
    

    

      Nothing errored. TypeScript is happy — the link was markup, not a type. No test failed, because no
      test knew the link was supposed to exist; it was added by hand, in a hurry, and nobody wrote a test
      for a link. You find out when a user emails you, or you don't find out.
    


    
Why it happens

    

      Not because the model is careless. Because the only place that link existed was inside forty files of
      implementation, and the model was shown four of them.
    

    

      Every regeneration is a lossy round trip: the intent goes in as a prompt, comes out as code, and the
      prompt is thrown away. Next time, the model has to recover the intent from the code — and it
      only reads the part of the code you handed it. Anything outside that window is not forgotten, exactly.
      It was never known.
    

    

      

        The generated code cannot be the record of what the app is supposed to be. It's the output. Outputs
        don't remember their inputs.
      

    


    
What would have to exist

    

      Something that states the app's shape, that is small enough to be read in full every single time, and
      that is the thing you edit rather than the thing you regenerate.
    

    

      Small is the hard requirement. A design document doesn't work, because nobody updates it and no model
      reads it. A test suite doesn't work, because tests assert behaviour, not structure, and you'd need one
      per link. It has to be short enough that "read the whole thing" is the default, not an effort.
    

    

      That is what a .ux file is. Twenty lines for a screen, including the link:
    


screen Checkout
  needs signed-in
  intent "Take payment and confirm the order"

  show order.total

  form Order
    phone required
    submit "Pay" -> pay(order)

  action "Resend code" -> resendCode(order)
  action "Back to cart" -> Cart

    

      Now the change is a one-line edit to the .ux, and the generated code is disposable. Regenerate
      the whole thing from scratch if you like — the resend action is still declared, so it's still there.
    


    
The part that surprised me

    

      I expected the value to be in generating code. It isn't. The value is that the file is small enough
      to be read completely, which changes what the model can reason about.
    

    

      A model editing one screen also reads app.map — the navigation graph, four lines for a small
      app — and can therefore tell that the screen it's editing is the only route to two others. That's a
      fact about the whole system, available while editing one file. You cannot get that from forty files
      you didn't load.
    


    
The honest limitation

    

      This only holds while the .ux stays ahead of the code. The moment someone hand-edits the
      generated output and doesn't reflect it back, the source of truth is a lie — and today nothing
      enforces that. Generated files are marked with a comment and the convention is to regenerate rather
      than patch, but a convention is not a guarantee.
    

    

      It's a real weakness, and it's worth knowing before you build a workflow on this.

Reviewing a UI before it exists

    

      "Where does Cancel go?" is a product decision. Today it gets made by whoever wrote the component,
      at 2am, by accident.
    


    

      Think about how a navigation decision actually gets made on most teams.
    

    

      Someone builds a checkout screen. It needs a Cancel button. They write
      navigate(-1), or they push to /cart, or they route home — whichever felt right
      while they were deep in a payment integration and Cancel was the least interesting thing on screen.
      It ships. Nine months later a support ticket reveals that cancelling a payment dumps you on the
      homepage with an abandoned cart and no explanation.
    

    

      Nobody decided that. It was a side effect of a line of code, in a diff that was reviewed for its
      payment logic.
    


    
The review problem

    

      Flows are among the most consequential decisions in an app and among the least reviewable. To answer
      "what happens when I tap Cancel" from a pull request, a reviewer has to read the component, resolve
      the router config, and hold the screen graph in their head. So they don't. They review the payment
      logic, which is legible, and the navigation goes through unexamined.
    

    

      Meanwhile the people who should weigh in — whoever owns the product, whoever owns support —
      can't read the diff at all.
    


    
What it looks like when flow is a first-class thing

    

      In .ux, navigation isn't buried in an implementation detail. It's the arrow, and a change to
      it is a change to one line:
    


  screen Checkout
     needs signed-in
     intent "Take payment and confirm the order"
-    action "Cancel" -> Catalog
+    action "Cancel" -> Cart

    

      That diff is reviewable by someone who has never opened a React file. It doesn't require a preview
      deploy or a walkthrough. And it can happen before the screen is built, when changing your mind
      costs a line instead of a sprint.
    


    
Two things the checker adds to review

    

      First, it catches the changes a reviewer would have to be superhuman to spot. Repoint one arrow and
      a screen can become unreachable — not broken, just orphaned, with no route to it from anywhere:
    


ux/screens/receipt.ux:3  UX201  Nothing links to `Receipt`, so no one can reach it.
  fix:  add an action on another screen:  action "…" -> Receipt

    

      Second, every screen has to say why it exists. intent is required — one line, plain language,
      or the file doesn't check:
    


screen Checkout
  intent "Take payment and confirm the order"

    

      That line costs nothing to write and it's the thing a reviewer reads first. It's also what makes the
      whole file worth reading six months later, when the author has left and the screen is called
      CheckoutV2Final.
    


    
Where this stops working

    

      A .ux file describes structure and flow, deliberately not appearance. It will tell you that
      Cancel goes back to the cart. It will not tell you that the button is the wrong shade of grey, or that
      the form is unusable on a small screen. Those still need eyes on a real build.
    

    

      What it buys you is that the decisions which are structural get reviewed structurally, instead
      of being smuggled through inside a payment diff.

Dead ends are not crashes

    

      A screen with no way out throws no exception, fails no test, and renders perfectly. That's exactly
      why it ships.
    


    

      Every tool in a normal build pipeline is looking for a moment where the program is wrong about
      itself. A type error: this value isn't what you said it was. A failing test: this function returned
      the wrong thing. A crash: this operation was impossible.
    

    

      Now consider a confirmation screen with no back button, no close, no continue. Nothing about it is
      wrong in that sense. The types are fine. It renders. It's fast. Every assertion anyone wrote about it
      passes. The only problem is that a person who arrives has nowhere to go, and no tool in the pipeline
      has a concept of "a person" or "go".
    


    
The class of bug

    

      These share a shape: correct code, wrong system. A few examples that all pass a normal
      build:
    

    
    
      
  • A screen nothing links to. It exists, it works, nobody can reach it.
    • 
      
  • A link to a screen that was renamed. In a typed router you'd catch it; in most apps it's a string.
    • 
      
  • A list that renders three items beautifully and shows a blank rectangle when the fetch fails.
    • 
      
  • A screen whose only exit runs a flow that navigates nowhere — a button that appears to leave and doesn't.
    • 
    

    

      None of these is detectable from one file. They're all facts about how the pieces relate, which means
      you need something holding the whole graph to see them.
    


    
What catching them looks like

    

      Because .ux records where every action leads, the graph exists as data, and the questions
      become mechanical:
    


$ ux check ux/
ux/screens/confirm.ux:4  UX202  `Confirm` has no way out — a user who lands here is stuck.
  fix:  add an action that leaves:  action "Back" -> Cart

ux/screens/inbox.ux:12  UX200  `Inbox` links to `Detials`, which does not exist.
  fix:  add `screen Detials` or `flow Detials`, or fix the spelling

2 error(s)
$ echo $?
1

    

      Non-zero exit, so it fails a build like anything else. Add ux check ux/ to CI and a stuck user
      becomes a red pipeline rather than a support ticket.
    


    
The detail that took three attempts to get right

    

      Deciding what counts as "a way out" is where this gets subtle, and getting it wrong makes the check
      worse than useless.
    

    

      A screen whose only action invokes a flow looked, at first, like a dead end — the arrow doesn't
      point at a screen. But if that flow ends in go Inbox, the user plainly does leave. Reporting
      it was a false alarm on a perfectly good app, and a checker that cries wolf gets muted, which costs
      you every real finding too.
    

    

      The opposite mistake is just as bad. A self-loop — action "Refresh" -> Home on Home — is
      technically an edge, and counting it means a genuinely stuck screen passes. So does
      action retry on a failed list: it re-runs the load, it doesn't take you anywhere.
    

    

      The rule that survived: an exit is an edge to a different screen, and a flow contributes the
      screens its go steps lead to. A flow with no go contributes nothing — correctly, since
      it leaves you where you were.
    


    
Why a language and not a linter

    

      You could write this as a lint rule over React. People have tried, and it's hard for a reason: you'd
      have to recover the navigation graph from router configuration, conditional pushes, and callbacks
      passed three components deep. The information is technically present and practically unrecoverable.
    

    

      The graph is easy to check when navigation is a declaration rather than a side effect. That's the
      whole argument for a separate language: not that .ux is nicer to write than JSX, but that it
      makes a specific class of question answerable.
