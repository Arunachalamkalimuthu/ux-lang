Use cases

Where a .ux file earns its keep.

The common thread: somebody needs to know what the app is supposed to do, and the code is the wrong place to ask. These are the situations where that costs you something real.

Building

The regeneration that loses a step

You ask for a change to the checkout screen. The model rewrites four files, and the "resend verification code" link that used to sit under the phone field is gone. Nothing errored. No test covered it, because no test knew it was supposed to be there.

This happens because the app's shape lives only in the generated code, and the model can't hold forty files at once. With a .ux file, the shape lives in one page it always sees. You change one line, regenerate, and what you didn't touch stays.

Review

Reviewing a flow before the code exists

"Where does Cancel go?" is a product decision, but today it is only answerable by reading a component tree or clicking through a preview build. So it gets decided by whoever wrote the component, at 2am, by accident.

A .ux diff shows a flow change as a flow change: 

  screen Checkout
     intent "Take payment and confirm the order"
-    action "Cancel" -> Cart
+    action "Cancel" -> Catalog

That is reviewable by someone who doesn't read React, in a pull request, before anything is built.

CI

Making a stuck user a failed build

A screen with no way out isn't a crash. It renders, it passes type-checking, every unit test is green, and a person who lands there has to kill the app. Nothing in a normal toolchain has the concept needed to notice. 

$ ux check ux/
ux/screens/confirm.ux:4  UX202  `Confirm` has no way out — a user who lands here is stuck.
  fix:  add an action that leaves:  action "Back" -> Cart

1 error(s)
$ echo $?
1

Same for a link to a screen nobody wrote, a screen nothing links to, and a list with no empty state. All of them exit non-zero, so they fail the build like anything else.

Onboarding

Answering "how does this fit together"

The first week on a new codebase is spent reconstructing a map that exists in nobody's head and no file. ux map prints it: 

Catalog       -> Cart | ProductDetail
ProductDetail -> Cart | Catalog
Cart          -> Catalog | Checkout | ProductDetail
Checkout      -> Cart | Catalog

Four lines, generated from the source, so it can't be out of date the way a wiki diagram always is. It's also what you hand a model before asking it to change anything.

Completeness

Forcing the states everyone skips

Generated UI is almost always the happy path. The list renders beautifully with three items and has nothing to say when the fetch fails, the result is empty, or it's still loading — because nothing ever made anyone decide.

In .ux a list without all three states doesn't check. It isn't a lint warning you can turn off; the file is invalid. It's the most opinionated rule in the language and the one that changes the most about what gets shipped.

Later

Agents that navigate a site instead of scraping it

The same format read in the other direction: an indexer walks a live page's accessibility tree and writes .ux. An agent then plans a route through a semantic map — a few hundred tokens, stable across redeploys — instead of paying tens of thousands of tokens for DOM that is mostly class hashes.

This is specified in the format design and deliberately not built. It's the larger half of the idea, and it needs the authoring half to be solid first.
