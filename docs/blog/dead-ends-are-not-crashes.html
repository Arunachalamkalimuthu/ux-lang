Dead ends are not crashes

A screen with no way out throws no exception, fails no test, and renders perfectly. That's exactly why it ships.

Every tool in a normal build pipeline is looking for a moment where the program is wrong about itself. A type error: this value isn't what you said it was. A failing test: this function returned the wrong thing. A crash: this operation was impossible.

Now consider a confirmation screen with no back button, no close, no continue. Nothing about it is wrong in that sense. The types are fine. It renders. It's fast. Every assertion anyone wrote about it passes. The only problem is that a person who arrives has nowhere to go, and no tool in the pipeline has a concept of "a person" or "go".

The class of bug

These share a shape: correct code, wrong system. A few examples that all pass a normal build:

  • A screen nothing links to. It exists, it works, nobody can reach it.
  • A link to a screen that was renamed. In a typed router you'd catch it; in most apps it's a string.
  • A list that renders three items beautifully and shows a blank rectangle when the fetch fails.
  • A screen whose only exit runs a flow that navigates nowhere — a button that appears to leave and doesn't.

None of these is detectable from one file. They're all facts about how the pieces relate, which means you need something holding the whole graph to see them.

What catching them looks like

Because .ux records where every action leads, the graph exists as data, and the questions become mechanical: 

$ ux check ux/
ux/screens/confirm.ux:4  UX202  `Confirm` has no way out — a user who lands here is stuck.
  fix:  add an action that leaves:  action "Back" -> Cart

ux/screens/inbox.ux:12  UX200  `Inbox` links to `Detials`, which does not exist.
  fix:  add `screen Detials` or `flow Detials`, or fix the spelling

2 error(s)
$ echo $?
1

Non-zero exit, so it fails a build like anything else. Add ux check ux/ to CI and a stuck user becomes a red pipeline rather than a support ticket.

The detail that took three attempts to get right

Deciding what counts as "a way out" is where this gets subtle, and getting it wrong makes the check worse than useless.

A screen whose only action invokes a flow looked, at first, like a dead end — the arrow doesn't point at a screen. But if that flow ends in go Inbox, the user plainly does leave. Reporting it was a false alarm on a perfectly good app, and a checker that cries wolf gets muted, which costs you every real finding too.

The opposite mistake is just as bad. A self-loop — action "Refresh" -> Home on Home — is technically an edge, and counting it means a genuinely stuck screen passes. So does action retry on a failed list: it re-runs the load, it doesn't take you anywhere.

The rule that survived: an exit is an edge to a different screen, and a flow contributes the screens its go steps lead to. A flow with no go contributes nothing — correctly, since it leaves you where you were.

Why a language and not a linter

You could write this as a lint rule over React. People have tried, and it's hard for a reason: you'd have to recover the navigation graph from router configuration, conditional pushes, and callbacks passed three components deep. The information is technically present and practically unrecoverable.

The graph is easy to check when navigation is a declaration rather than a side effect. That's the whole argument for a separate language: not that .ux is nicer to write than JSX, but that it makes a specific class of question answerable.
